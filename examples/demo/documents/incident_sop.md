# 故障处理 SOP

## 1. 故障分级

### Severity 定义

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|---------|------|
| P0 | 核心服务完全不可用 | 15分钟 | 支付服务宕机 |
| P1 | 核心服务部分不可用 | 30分钟 | 订单查询缓慢 |
| P2 | 非核心服务故障 | 2小时 | 后台报表延迟 |
| P3 | 轻微影响 | 24小时 | 页面样式问题 |

## 2. 故障处理流程

### 2.1 发现阶段

**自动发现：**
- Prometheus 告警触发
- 日志异常检测
- 用户反馈系统

**手动上报：**
- 值班人员接收
- 确认故障级别

### 2.2 响应阶段

**立即行动（P0/P1）：**

1. 在故障群通告
2. 评估影响范围
3. 启动紧急响应
4. 通知相关方

### 2.3 诊断阶段

**系统排查路径：**

```
用户反馈
  ↓
检查 API 网关（是否限流/超时）
  ↓
检查服务状态（kubectl get pods）
  ↓
检查日志（kubectl logs）
  ↓
检查数据库（连接数/慢查询）
  ↓
检查依赖服务（Redis/MQ/外部 API）
  ↓
确定根因
```

### 2.4 修复阶段

**常见故障修复：**

| 故障类型 | 紧急修复 | 长期修复 |
|---------|---------|---------|
| Pod OOM | 增加 Memory Limit | 优化内存使用 + HPA |
| 数据库连接满 |  kill 空闲连接 | 连接池优化 + 扩容 |
| API 超时 | 临时增加超时 | 性能优化 + 缓存 |
| 磁盘满 | 清理日志 | 日志轮转 + 扩容 |
| DNS 解析失败 | 重启 CoreDNS | 检查 DNS 配置 |

## 3. 值班制度

### 3.1 值班安排
- 主值班: 9:00 - 21:00
- 备值班: 21:00 - 9:00
- 每两周轮换

### 3.2 值班职责
- 5分钟内响应告警
- 15分钟内确认故障
- 30分钟内启动处理流程
- 全程记录处理过程
